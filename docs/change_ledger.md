# 改动验证台账

> **这份文档回答一个问题：哪些改动真的被验证过？**
>
> 建立动机（2026-09-14，用户指出）：改动一直在累加，失败的趟次没有回撤过，
> 于是"哪些改动是有效的"变成了没人答得上来的问题。**没有这份台账，每一次
> 失败都无法归因，每一个改动都只能永远留在树上。**

## 两个必须分开的概念

| | 含义 |
|---|---|
| **跑过** | 这个改动在某趟真实训练里执行过 |
| **已验证** | 有一趟**跑完并出分**的实验，能说明它做到了它声称的事 |

**"跑过"不等于"已验证"。**一趟在 step 10 OOM 掉的训练，其中的改动只是跑过，
没有任何证据说明它对不对。本项目此前一直把两者混为一谈。

## run → commit 这条链已经是通的

`run_metaclaw_migration_modelfactory.sh:49` 取 `git rev-parse --short HEAD`，
写进 `${LOGS_DIR}/RUN_MANIFEST.txt` 第一行，并拼进 wandb group 名。
**所以任何一趟都能查到它用的代码版本，缺的从来不是记录，是回头看。**

查某趟用了哪个 commit：

```bash
head -1 /dfs/data/openclaw-rl-project/logs/metaclaw_migration_<RUN_ID>/RUN_MANIFEST.txt
```

## 已知的归因陷阱（下一趟必须带着这个读结果）

**(a) 轨迹级样本取代 1/N，不是叠加**——整轮变一个样本，N=1，1/N 自动失效。
所以做 (a) 不必先验证 1/N。

**但轮边界与归属那几个修复（`1fd5f25` + `e7979e1`）在两种模式下都压在底下**，
(a) 同样依赖它们判断哪些 turn 属于本轮。

> ⚠️ **所以下一趟如果失败，嫌疑人名单里必须同时包含 (a)、`1fd5f25`、`e7979e1`，
> 不能只怪 (a)。** 这正是此前反复出现的"失败了但不知道怪谁"。

## 维护规则

1. **每趟跑完就更新本表**——把该趟的 commit 填进"已验证"或写明为什么不算
2. **不更新 = 那趟没有结论**，不要事后凭印象补
3. 一个改动连续两趟都拿不到"已验证"，**就该进回撤讨论**，而不是继续留在树上
